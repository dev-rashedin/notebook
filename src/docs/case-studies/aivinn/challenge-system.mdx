## Background & Problem Statement

Aivinn's Challenges feature lets users opt into system-generated financial habit challenges (e.g. "Avoid Coffee & Snacks," "Track Expenses Daily"). Unlike Goals, Challenges are **not user-editable** — they're suggested by the system, accepted by the user, and tracked automatically.

The original implementation had two tools (`AssignChallengeTool`, `IncrementChallengeTool`) wired into an AI agent, plus a partial evaluation function (`evaluateChallengeProgress`) that only handled 2 of 5 challenge types. The system had three concrete problems:

1. **No proactive suggestion path.** Challenges were only ever suggested reactively, when a user's chat message happened to match a category keyword. A user (including our own CEO) who never typed something like "I want to save on coffee" would simply never receive a challenge.
2. **Three of five challenge types were dead code.** `AVOID`, `STREAK`, and `SAVE` types existed in the schema and had seed data, but nothing ever evaluated their progress — they'd sit at 0% forever.
3. **No lifecycle management.** Challenges never expired, never got cleaned up, and stale `SUGGESTED` rows could accumulate indefinitely.

This case study documents the full redesign: five cron jobs, a rewritten evaluation pipeline, and tool-layer fixes — built incrementally, with each architectural decision made deliberately rather than assumed.

## System Architecture Decisions

Before writing any code, several foundational questions needed answers. Getting these wrong early would have meant rebuilding later.

### Decision 1: User-centric, not wallet-centric

**The question:** Aivinn wallets can be shared between multiple users. Should a challenge belong to a wallet (shared) or a user (individual)?

**The answer:** Challenges belong to the **wallet owner only** — never to wallet members. This was already implicit in the schema (`user_challenges` has both `user_id` and `wallet_id`, with the uniqueness constraint keyed on `user_id`), but needed to be made explicit as a rule: `wallet_id` exists purely to know *which wallet's transactions to evaluate against*, not to determine *who* the challenge belongs to.

**Why this matters:** if two people share a wallet, only the owner receives suggestions and notifications. This avoids ambiguity around "whose challenge is this" and "who gets credit" — decisions that would otherwise need their own arbitration logic.

### Decision 2: Concurrency cap — 3 total, 2 suggested

A user can have at most **3 challenges in play at once** (combined `SUGGESTED` + `ACTIVE`), with a sub-limit of **2 in `SUGGESTED` state**. This means:

| Active count | Max additional Suggested |
|---|---|
| 0 | 2 |
| 1 | 2 |
| 2 | 1 |
| 3 | 0 |

**Why:** an earlier draft capped it at just 1 in-flight suggestion, which felt too restrictive — offering almost nothing to engage with. But no cap at all risks overwhelming the user with a wall of suggestions. 3/2 was chosen as a middle ground: enough variety to feel alive, tight enough to stay uncluttered.

### Decision 3: Expiry over deletion where possible

Two different cleanup philosophies were needed for two different states:

- **Unaccepted `SUGGESTED` challenges** → hard-deleted after 2 weeks. There's no analytical value in a suggestion nobody engaged with, and no field was added to track "why" — it's just gone.
- **Resolved `EXPIRED`/`COMPLETED` challenges** → kept for 3 months before deletion. This preserves a window for analytics (completion rates, reward history) before the row is purged.

**Why the asymmetry:** unaccepted suggestions carry no signal — a user never even looked at it. Resolved challenges carry real signal (user engaged, succeeded or failed) and are worth retaining briefly for product insight.

### Decision 4: `rules.evaluation_window_days` over `challenges.duration_days` as the source of truth

The `challenges` table has a `duration_days` column, and the JSON `rules` field (personalized per user at assignment time) has its own `evaluation_window_days`. These *can* diverge — the assignment tools only ever read/write `evaluation_window_days`, never touching `duration_days`. Using the wrong one would mean expiry timing silently drifting from what the user was actually told.

**Resolution:** every expiry/deadline calculation in the system reads `user_challenges.rules.evaluation_window_days`, falling back to a default (30 days) if absent. `duration_days` is effectively legacy and unused going forward.

### Decision 5: Type-specific failure semantics

Not all challenge types fail the same way. This took the most back-and-forth to settle:

- **AVOID** ("don't spend on X for N days"): a single violating transaction should **fail the challenge immediately** — there's no partial credit for "mostly avoiding" something you were told to avoid entirely.
- **STREAK** ("do X daily for N days"): a missed day should **reset progress to 0, not fail the challenge outright** — the user still has the remaining window to build a fresh streak. This was a deliberate UX choice: a punitive "one missed day = game over" felt discouraging, whereas a reset-and-encourage approach ("Streak Broken 💔 — log a transaction today to start again!") keeps the user engaged rather than abandoning ship.
- **LIMIT / SAVE**: these are threshold-based, not event-based — progress is a continuous ratio (spend vs. limit, or savings vs. goal), recalculated daily/on-transaction until the window closes.

## AI Tool Layer

### AssignChallengeTool

This is the entry point when a user expresses challenge-relevant intent through chat (e.g. "I want to spend less on coffee").

**Original design flaw:** the tool only matched challenges of type `LIMIT` or `FREQUENCY` (an MVP-era restriction), always picked the first matching challenge deterministically (`matchedChallenges[0]`), and had no concept of the concurrency cap — a chat-triggered assignment could push a user past the 3/2 limit that the cron jobs otherwise respect.

**Final implementation:**

```typescript
export const AssignChallengeTool = tool(
  async ({
    userId,
    walletId,
    userInput,
  }: {
    userId: string;
    walletId: string;
    userInput: string;
  }) => {
    // 0️⃣ Cap check — before anything else
    const underCap = await userChallengesService.isUnderChallengeCap(userId);
    if (!underCap) {
      return {
        success: true,
        challenge: null,
        message: `You've already got challenges lined up! Finish or check your current ones on the Challenges screen before starting new ones.`,
      };
    }

    // 1️⃣ Fetch categories (SOURCE OF TRUTH)
    const categories = await categoriesService.fetchCategories();

    // 2️⃣ Strict category detection (NO GUESSING)
    const normalizedInput = userInput.toLowerCase();
    const matchedCategory = categories.find(cat => {
      const keywords = cat.name.toLowerCase().split(/[\s&]+/);
      return keywords.some(kw => normalizedInput.includes(kw));
    });

    if (!matchedCategory) {
      return {
        success: true,
        challenge: null,
        message:
          'I couldn\u2019t clearly match your request to a specific category. You can create a custom goal from the Goals screen.',
      };
    }

    // 3️⃣ Fetch challenges
    const challenges = await challengesService.fetchAllChallenges();

    // 4️⃣ Match by category — ALL types now, not just LIMIT/FREQUENCY
    const matchedChallenges = challenges.filter(ch => {
      const rules = ch.rules as { trigger_category?: string };
      return rules.trigger_category === matchedCategory.name;
    });

    if (matchedChallenges.length === 0) {
      return {
        success: true,
        challenge: null,
        message: `There\u2019s no challenge available yet for "${matchedCategory.name}". You can create a custom goal to track this from the Goals screen.`,
      };
    }

    // 5️⃣ Pick best candidate using shared tier-priority logic
    const selectedChallenge = await userChallengesService.pickBestCandidate(userId, matchedChallenges);

    // 6️⃣ Fetch user metrics (last 30 days)
    const userMetrics = await challengesService.getUserMetrics(userId, walletId);

    // 7️⃣ Prepare personalized rules
    const baseRules = selectedChallenge.rules as any;
    const personalizedRules = { ...baseRules };

    if (baseRules.min_spend_threshold && userMetrics.categorySpend) {
      const userSpent = Math.abs(userMetrics.categorySpend[matchedCategory.id] ?? 0);
      personalizedRules.min_spend_threshold = Math.max(
        baseRules.min_spend_threshold ?? 1,
        Math.round(userSpent * 0.8),
      );
    }

    if (!baseRules.evaluation_window_days) {
      personalizedRules.evaluation_window_days = 30;
    }

    if (baseRules.frequency_target) {
      const freq = userMetrics.frequency[matchedCategory.name] ?? 0;
      personalizedRules.frequency_target = Math.max(baseRules.frequency_target, freq);
    }

    personalizedRules.progress_target = baseRules.progress_target ?? 100;

    // 8️⃣ Assign challenge as SUGGESTED with personalized rules
    await userChallengesService.assignChallengeToUser(
      selectedChallenge.id,
      walletId,
      personalizedRules,
    );

    const friendlyMessage = `I've suggested a challenge for you: "${selectedChallenge.title}" — ${selectedChallenge.description}. You've got ${personalizedRules.evaluation_window_days || 7} days. Start it from the Challenges screen whenever you're ready!`;

    return {
      success: true,
      challenge: {
        id: selectedChallenge.id,
        title: selectedChallenge.title,
        description: selectedChallenge.description,
        rules: personalizedRules,
      },
      message: friendlyMessage,
    };
  },
  {
    name: 'assign_challenge',
    description: `
Suggest a challenge ONLY when user intent clearly matches an existing category from database.
No guessing. No fallback. No cross-category suggestions.
If no match → guide user to create custom goal.
Respects the user's challenge cap (max 3 total, max 2 suggested) — will decline if already at cap.
`,
    schema: z.object({
      userId: z.string(),
      walletId: z.string(),
      userInput: z.string(),
    }),
  },
);
```

**Why personalization matters:** `min_spend_threshold` is adjusted to 80% of the user's actual recent spend in that category (never below the template's floor). A flat, un-personalized limit would be either trivially easy (irrelevant to a low spender) or impossibly hard (unfair to a high spender). Personalizing it against real `getUserMetrics` data makes the challenge meaningfully calibrated per user.

**Why strict category matching, no fallback:** the tool description explicitly forbids guessing. Financial suggestions carry real weight — assigning the wrong challenge based on a loose keyword match (e.g. matching "car" to "Transportation" when the user meant something else) erodes trust in the AI's judgment. If nothing matches cleanly, the tool declines and redirects to Goals instead of guessing.

### IncrementChallengeTool

Called when a user explicitly reports progress in chat (e.g. "I avoided coffee today").

**Original design flaw:** the schema required a `userId` parameter that the function body never used — dead input, and a missed opportunity for a safety check.

**Final implementation:**

```typescript
export const IncrementChallengeTool = tool(
  async ({
    userId,
    walletId,
    challengeId,
    amount,
  }: {
    userId: string;
    walletId: string;
    challengeId: string;
    amount: number;
  }) => {
    if (amount <= 0 || amount > 50) {
      return {
        success: false,
        message: 'Invalid amount. Must be between 1 and 50 progress points.',
      };
    }

    // Safety check: ensure this challenge actually belongs to the requesting user
    const userChallenge = await prisma.user_challenges.findFirst({
      where: { wallet_id: walletId, OR: [{ challenge_id: challengeId }, { id: challengeId }] },
      select: { user_id: true },
    });

    if (!userChallenge || userChallenge.user_id !== userId) {
      return {
        success: false,
        message: 'Challenge not found for this user.',
      };
    }

    const updatedChallenge = await userChallengesService.incrementProgressOrMarkCompleted(
      walletId,
      challengeId,
      amount,
    );

    return {
      success: true,
      data: updatedChallenge,
      message:
        updatedChallenge.status === 'COMPLETED'
          ? 'Challenge completed and reward granted!'
          : `Challenge progress updated to ${updatedChallenge.progress}%`,
    };
  },
  {
    name: 'increment_challenge',
    description: `
Increment the progress of a user's ACTIVE challenge.

Only call this when a user explicitly mentions an action related to a challenge
(e.g. "I avoided coffee today", "I cooked at home this week").

Do NOT call this for regular transactions — those are handled automatically.

You must provide:
- userId
- walletId
- challengeId: the challenge template id (challenges.id from app_context, NOT user_challenges.id)
- amount: progress points to add (between 1 and 50)
`,
    schema: z.object({
      userId: z.string(),
      walletId: z.string(),
      challengeId: z.string().describe('challenges.id from app_context — not user_challenges.id'),
      amount: z.number().min(1).max(50),
    }),
  },
);
```

**Why add the ownership check:** `challengeId` is AI-supplied from conversation context, not deterministically fetched. If the model ever hallucinates or carries over a stale ID from a different user's context, incrementing progress on the wrong person's challenge would be a real data integrity bug. The check costs one indexed query and closes that gap outright — using data (`userId`) the tool was already receiving but silently discarding.

## Transaction-Triggered Evaluation

`evaluateChallengeProgress` runs on every transaction create, update, and delete. It's the reactive half of the system — the half that responds instantly to user behavior, as opposed to the cron jobs, which handle everything time-based or passive.

**Why some logic lives here and not in cron:** anything that needs to react *the moment* a transaction happens — like an AVOID challenge failing the instant a disqualifying purchase is logged — can't wait for a daily cron run. A day's delay between the violation and the notification would feel broken; the user would keep thinking their challenge was still alive.

```typescript
export const evaluateChallengeProgress = async (
  walletId: string,
  transaction: {
    categoryName: string;
    categoryId: string;
    amount: Decimal | number;
    type: 'INCOME' | 'EXPENSE';
  },
) => {
  if (transaction.type !== 'EXPENSE') return;

  const activeChallenges = await prisma.user_challenges.findMany({
    where: { wallet_id: walletId, status: 'ACTIVE' },
    include: { challenges: { select: { type: true, title: true } } },
  });

  if (activeChallenges.length === 0) return;

  for (const userChallenge of activeChallenges) {
    const rules = userChallenge.rules as {
      trigger_category?: string;
      evaluation_window_days?: number;
      min_spend_threshold?: number;
      min_occurrences?: number;
    } | null;

    if (!rules?.trigger_category) continue;
    if (rules.trigger_category.toLowerCase() !== transaction.categoryName.toLowerCase()) continue;

    const challengeType = userChallenge.challenges?.type;
    let increment = 0;

    if (challengeType === 'LIMIT') {
      const windowStart = dayjs
        .utc(userChallenge.accepted_at ?? userChallenge.suggested_at)
        .startOf('day')
        .toDate();

      const spendAgg = await prisma.transactions.aggregate({
        where: {
          wallet_id: walletId,
          category_id: transaction.categoryId,
          type: 'EXPENSE',
          date: { gte: windowStart },
        },
        _sum: { amount: true },
      });
      const totalSpent = Math.abs(Number(spendAgg._sum.amount ?? 0));
      const threshold = rules.min_spend_threshold ?? 1;
      const spendRatio = Math.min(totalSpent / threshold, 1);
      const newProgress = Math.round(spendRatio * 100);

      await prisma.user_challenges.update({
        where: { id: userChallenge.id },
        data: { progress: newProgress, last_updated_at: new Date() },
      });

      const windowEnd = dayjs(userChallenge.accepted_at ?? userChallenge.suggested_at)
        .add(rules.evaluation_window_days ?? 7, 'day')
        .startOf('day');
      const today = dayjs().startOf('day');
      const windowExpired = today.isSame(windowEnd) || today.isAfter(windowEnd);

      if (windowExpired && totalSpent < threshold && !userChallenge.completed_rewarded) {
        await incrementProgressOrMarkCompleted(userChallenge.wallet_id, userChallenge.challenge_id, 100);
      }
      continue;
    } else if (challengeType === 'FREQUENCY') {
      increment = 10;
    } else if (challengeType === 'AVOID') {
      // Any matching transaction immediately fails an AVOID challenge
      await prisma.user_challenges.update({
        where: { id: userChallenge.id },
        data: { status: 'EXPIRED', last_updated_at: new Date() },
      });

      await sendPushNotification({
        userId: userChallenge.user_id,
        title: 'Challenge Failed',
        body: `Your "${userChallenge.challenges?.title}" challenge ended early due to a matching transaction.`,
        type: 'CHALLENGE',
        entityId: userChallenge.challenge_id,
        invalidateKeys: ['user-challenges'],
        data: { screen: 'Challenges' },
      });
      continue;
    } else {
      // STREAK, SAVE — not transaction-driven, handled entirely by the daily cron
      continue;
    }

    if (increment > 0) {
      await incrementProgressOrMarkCompleted(userChallenge.wallet_id, userChallenge.challenge_id, increment);
    }
  }
};
```

**Why AVOID lives here but STREAK and SAVE don't:** AVOID's success condition is defined by the *absence* of a matching transaction — its failure condition is the *presence* of one, which is inherently event-driven. STREAK ("did the user log something today") and SAVE ("what's the net income-minus-expenses so far") are both aggregate, time-window questions that only make sense to answer once per day, not on every individual transaction. Trying to evaluate a streak or savings target on every transaction would be both wasteful (recomputing the same daily aggregate repeatedly) and semantically wrong (a single transaction doesn't determine a streak).

## Cron Jobs

Five daily jobs were built, each with a distinct, non-overlapping responsibility. All run via `node-cron` against `config.cron_timezone` (Europe/Stockholm).

### 1. `expiredSuggestionsCleanupJob`

**Purpose:** deletes `SUGGESTED` challenges nobody ever accepted, after 2 weeks.

```typescript
// Cron: Deletes SUGGESTED challenges that were never accepted within 2 weeks (hard delete).
export const expiredSuggestionsCleanupJob = () => {
  cron.schedule(
    '30 2 * * *',
    async () => {
      try {
        const result = await prisma.user_challenges.deleteMany({
          where: {
            status: 'SUGGESTED',
            accepted_at: null,
            suggested_at: { lt: new Date(Date.now() - 14 * 24 * 60 * 60 * 1000) },
          },
        });
        console.log(`[ExpiredSuggestionsCleanup] Deleted ${result.count} unaccepted suggestions`);
      } catch (err) {
        console.error('[ExpiredSuggestionsCleanup] Failed:', err);
      }
    },
    config.cron_timezone,
  );
};
```

**Why hard delete, no status transition:** unlike resolved challenges (which carry analytical value), an unaccepted suggestion represents a decision the user never made. There's nothing to learn from it that the raw suggestion count elsewhere in the system doesn't already tell you. Keeping the row around indefinitely just accumulates clutter blocking the suggestion cap slot it was occupying.

### 2. `expiredChallengesJob` — the core resolution engine

**Purpose:** the single daily pass that resolves every ACTIVE challenge type. This is the most complex job in the system, because each challenge type has fundamentally different resolution logic.

```typescript
// Cron: Daily evaluation and resolution for all ACTIVE challenges.
// - AVOID: increments time-based progress daily; completes once the window ends violation-free
//   (violations are caught instantly elsewhere, in evaluateChallengeProgress).
// - STREAK: checks for a transaction logged yesterday; increments progress on a hit, resets
//   progress to 0 with a "streak broken" notification on a miss, and expires only if the
//   evaluation window closes before reaching 100%.
// - SAVE: recalculates net savings (income − expenses) since the challenge started and updates
//   progress to reflect real savings, completing once the threshold is met.
// - LIMIT / FREQUENCY: resolved once, the day after the evaluation window closes — LIMIT gets a
//   safety-net check (marks COMPLETED if spend stayed under threshold even without a final
//   triggering transaction), otherwise the challenge is marked EXPIRED.
// All resolutions (COMPLETED/EXPIRED) send a push notification to the user.
import dayjs from 'dayjs';
import isSameOrAfter from 'dayjs/plugin/isSameOrAfter';
dayjs.extend(isSameOrAfter);
import cron from 'node-cron';
import prisma from '../lib/prisma';
import { sendPushNotification } from '../lib/push-notification';
import { userChallengesService } from '../app/modules/challenges/user-challenges.service';
import config from '../app/config';

const expireChallenge = async (uc: any) => {
  await prisma.user_challenges.update({
    where: { id: uc.id },
    data: { status: 'EXPIRED', last_updated_at: new Date() },
  });
  await sendPushNotification({
    userId: uc.user_id,
    title: 'Challenge Expired',
    body: `Your "${uc.challenges.title}" challenge has ended.`,
    type: 'CHALLENGE',
    entityId: uc.challenge_id,
    invalidateKeys: ['user-challenges'],
    data: { screen: 'Challenges' },
  });
};

export const expiredChallengesJob = () => {
  cron.schedule(
    '0 9 * * *',
    async () => {
      try {
        const activeChallenges = await prisma.user_challenges.findMany({
          where: { status: 'ACTIVE' },
          include: { challenges: { select: { title: true, type: true } } },
        });

        const now = dayjs();
        let expiredCount = 0;
        let limitResolvedCount = 0;

        for (const uc of activeChallenges) {
          const rules = uc.rules as {
            evaluation_window_days?: number;
            min_spend_threshold?: number;
            trigger_category?: string;
          } | null;
          const windowDays = rules?.evaluation_window_days ?? 30;

          const startDate = uc.accepted_at ?? uc.suggested_at;
          if (!startDate) continue;

          const deadline = dayjs(startDate).add(windowDays, 'day');
          const pastDeadline = now.isSameOrAfter(deadline);

          // AVOID
          if (uc.challenges.type === 'AVOID') {
            if (pastDeadline) {
              await userChallengesService.incrementProgressOrMarkCompleted(uc.wallet_id, uc.challenge_id, 100);
            } else {
              const elapsedDays = now.diff(dayjs(startDate), 'day');
              const newProgress = Math.min(Math.round((elapsedDays / windowDays) * 100), 100);
              if (newProgress !== uc.progress) {
                await prisma.user_challenges.update({
                  where: { id: uc.id },
                  data: { progress: newProgress, last_updated_at: new Date() },
                });
              }
            }
            continue;
          }

          // STREAK
          if (uc.challenges.type === 'STREAK') {
            const yesterdayStart = now.subtract(1, 'day').startOf('day').toDate();
            const yesterdayEnd = now.startOf('day').toDate();

            const txCount = await prisma.transactions.count({
              where: { wallet_id: uc.wallet_id, date: { gte: yesterdayStart, lt: yesterdayEnd } },
            });

            let newProgress = uc.progress;

            if (txCount > 0) {
              newProgress = Math.min(uc.progress + Math.round(100 / windowDays), 100);
              if (newProgress >= 100) {
                await userChallengesService.incrementProgressOrMarkCompleted(uc.wallet_id, uc.challenge_id, 100);
              } else {
                await prisma.user_challenges.update({
                  where: { id: uc.id },
                  data: { progress: newProgress, last_updated_at: new Date() },
                });
              }
            } else if (uc.progress > 0) {
              newProgress = 0;
              await prisma.user_challenges.update({
                where: { id: uc.id },
                data: { progress: 0, last_updated_at: new Date() },
              });
              await sendPushNotification({
                userId: uc.user_id,
                title: 'Streak Broken 💔',
                body: `Your "${uc.challenges.title}" streak reset — log a transaction today to start again!`,
                type: 'CHALLENGE',
                entityId: uc.challenge_id,
                invalidateKeys: ['user-challenges'],
                data: { screen: 'Challenges' },
              });
            }

            if (pastDeadline && newProgress < 100) await expireChallenge(uc);
            continue;
          }

          // SAVE
          if (uc.challenges.type === 'SAVE') {
            const savingsAgg = await prisma.transactions.groupBy({
              by: ['type'],
              where: { wallet_id: uc.wallet_id, date: { gte: startDate } },
              _sum: { amount: true },
            });

            const income = Math.abs(savingsAgg.find(t => t.type === 'INCOME')?._sum.amount?.toNumber() ?? 0);
            const expenses = Math.abs(savingsAgg.find(t => t.type === 'EXPENSE')?._sum.amount?.toNumber() ?? 0);
            const netSavings = income - expenses;

            const threshold = rules?.min_spend_threshold ?? 1;
            const newProgress = Math.min(Math.max(Math.round((netSavings / threshold) * 100), 0), 100);

            if (newProgress >= 100) {
              await userChallengesService.incrementProgressOrMarkCompleted(uc.wallet_id, uc.challenge_id, 100);
            } else if (newProgress !== uc.progress) {
              await prisma.user_challenges.update({
                where: { id: uc.id },
                data: { progress: newProgress, last_updated_at: new Date() },
              });
            }

            if (pastDeadline && newProgress < 100) await expireChallenge(uc);
            continue;
          }

          // LIMIT / FREQUENCY — resolved once, the day after deadline
          const expiredYesterday =
            deadline.isAfter(now.subtract(2, 'day')) && deadline.isBefore(now.startOf('day'));
          if (!expiredYesterday || uc.progress >= 100) continue;

          if (uc.challenges.type === 'LIMIT' && rules?.trigger_category) {
            const spendAgg = await prisma.transactions.aggregate({
              where: {
                wallet_id: uc.wallet_id,
                type: 'EXPENSE',
                date: { gte: startDate },
                categories: { name: rules.trigger_category },
              },
              _sum: { amount: true },
            });
            const totalSpent = Math.abs(Number(spendAgg._sum.amount ?? 0));
            const threshold = rules.min_spend_threshold ?? 1;

            if (totalSpent < threshold) {
              await userChallengesService.incrementProgressOrMarkCompleted(uc.wallet_id, uc.challenge_id, 100);
              limitResolvedCount++;
              continue;
            }
          }

          await expireChallenge(uc);
          expiredCount++;
        }

        console.log(
          `[ExpiredChallenges] Expired ${expiredCount}, resolved ${limitResolvedCount} via LIMIT safety-net`,
        );
      } catch (err) {
        console.error('[ExpiredChallenges] Failed:', err);
      }
    },
    config.cron_timezone,
  );
};
```

**Why one job handles five different resolution strategies instead of five separate jobs:** all five types share the same iteration surface (`ACTIVE` challenges) and the same daily cadence. Splitting them into separate jobs would mean five separate queries fetching largely overlapping data, and — more importantly — five places where the deadline-calculation logic (`rules.evaluation_window_days`, `pastDeadline`) could drift out of sync with each other if one got updated and the others didn't. One job, branching by type, keeps the shared primitives (deadline math, `expireChallenge`) genuinely shared.

**A real bug caught during this design (worth documenting):** an early version of the STREAK/SAVE branches checked the stale `uc.progress` (fetched before the loop's mutations) when deciding whether to also expire the challenge. This meant a challenge that had *just* been marked COMPLETED in the same pass could immediately be marked EXPIRED right after — because the deadline check was comparing against the old, pre-update progress value. Fixed by tracking `newProgress` locally within each branch and using that for the expiry decision instead.

**The LIMIT safety-net, explained:** `evaluateChallengeProgress` normally resolves a LIMIT challenge's final outcome only when a *transaction* triggers the check near the window's end. But if the user simply doesn't transact again in that category after their last purchase, nothing ever fires that final check — the challenge would sit at, say, 40% progress forever, even if the user genuinely succeeded (stayed under threshold). The safety-net closes this: the cron independently re-checks total spend against the threshold once the window has closed, regardless of whether a transaction happened to trigger it.

### 3. `oldChallengesCleanupJob`

**Purpose:** purges resolved challenge history after 3 months.

### 4. `proactiveSuggestionJob` — solving the "no regular challenges" problem

**Purpose:** this is the direct fix for the original complaint (the CEO never receiving challenges). It runs daily, scans every wallet, and — for users under the concurrency cap — assigns a new challenge based on real spending metrics, without requiring any chat interaction.

```typescript
// Cron: Proactively suggests a new challenge to users under the suggestion cap, based on their
// actual spending patterns (category-matched) or global habit-building challenges. Picks are
// prioritized via the shared pickBestCandidate helper: never-assigned > previously failed >
// previously succeeded, random among ties. Cap enforced via shared isUnderChallengeCap helper —
// same logic AssignChallengeTool uses, so both stay in sync.
import cron from 'node-cron';
import prisma from '../lib/prisma';
import { sendPushNotification } from '../lib/push-notification';
import { userChallengesService } from '../app/modules/challenges/user-challenges.service';
import { challengesService } from '../app/modules/challenges/challenges.service';
import config from '../app/config';

export const proactiveSuggestionJob = () => {
  cron.schedule(
    '0 10 * * *',
    async () => {
      try {
        const wallets = await prisma.wallets.findMany({
          select: { id: true, owner_id: true, name: true },
        });

        let assignedCount = 0;

        for (const wallet of wallets) {
          const userId = wallet.owner_id;

          const underCap = await userChallengesService.isUnderChallengeCap(userId);
          if (!underCap) continue;

          const metrics = await challengesService.getUserMetrics(userId, wallet.id);
          const spentCategoryIds = Object.keys(metrics.categorySpend).filter(
            id => Math.abs(metrics.categorySpend[id]) > 0,
          );

          const categories = spentCategoryIds.length
            ? await prisma.categories.findMany({
                where: { id: { in: spentCategoryIds } },
                select: { id: true, name: true },
              })
            : [];
          const nameToId = new Map(categories.map(c => [c.name, c.id]));

          const allChallenges = await prisma.challenges.findMany({ where: { is_active: true } });

          const candidates = allChallenges.filter(ch => {
            const rules = ch.rules as { trigger_category?: string } | null;
            if (!rules?.trigger_category) return true; // global — always a candidate
            return nameToId.has(rules.trigger_category);
          });

          if (candidates.length === 0) continue;

          const chosen = await userChallengesService.pickBestCandidate(userId, candidates);

          const baseRules = chosen.rules as any;
          const personalizedRules = { ...baseRules };

          if (baseRules?.min_spend_threshold && baseRules?.trigger_category) {
            const categoryId = nameToId.get(baseRules.trigger_category);
            const userSpent = categoryId ? Math.abs(metrics.categorySpend[categoryId] ?? 0) : 0;
            personalizedRules.min_spend_threshold = Math.max(
              baseRules.min_spend_threshold ?? 1,
              Math.round(userSpent * 0.8),
            );
          }

          await userChallengesService.assignChallengeToUser(chosen.id, wallet.id, personalizedRules);

          await sendPushNotification({
            userId,
            title: 'New Challenge Suggested! 💡',
            body: `We picked "${chosen.title}" for your "${wallet.name}" wallet — check it out on the Challenges screen.`,
            type: 'CHALLENGE',
            entityId: chosen.id,
            invalidateKeys: ['user-challenges'],
            data: { screen: 'Challenges' },
          });

          assignedCount++;
        }

        console.log(`[ProactiveSuggestion] Assigned ${assignedCount} new challenge suggestions`);
      } catch (err) {
        console.error('[ProactiveSuggestion] Failed:', err);
      }
    },
    config.cron_timezone,
  );
};
```

**Why daily cron and not per-transaction:** proactive suggestion is fundamentally a discovery problem — "here's something you *haven't* been doing" — evaluated against a 30-day rolling view of spending (`getUserMetrics`), not a single event. Running this per-transaction would mean redundant recomputation on every logged expense and risk firing multiple suggestion attempts in rapid succession if a user logs several transactions in one sitting. A daily cadence naturally throttles this to one meaningful check per day.

**Why global (non-category) challenges are included as candidates:** initially the job only considered category-matched challenges (LIMIT/AVOID/FREQUENCY tied to actual spending categories). But this meant users with weak or scattered spending patterns — or ones who'd exhaust their obvious category matches — would never see habit-building challenges like "Track Expenses Daily." Including global challenges in the same candidate pool, subject to the same tier-priority picking, ensures variety without requiring a special-case fallback path.

### 5. `reactivationJob` — the inactivity-driven flows

**Purpose:** re-engage users who've gone quiet, through two independent signals.

```typescript
// Cron: Reactivation checks for lapsed users.
// - No transaction logged in 14 days → assign "Get Back on Track" challenge (respects the same
//   SUGGESTED+ACTIVE cap as the proactive suggestion job) + notification.
// - No app open (users.last_active_at) in 14/21 days → notification only, no challenge. Computed
//   live off last_active_at age — no dedup field needed, fires once at day 14, once at day 21.
import cron from 'node-cron';
import dayjs from 'dayjs';
import prisma from '../lib/prisma';
import { sendPushNotification } from '../lib/push-notification';
import { userChallengesService } from '../app/modules/challenges/user-challenges.service';
import config from '../app/config';

const GET_BACK_ON_TRACK_TITLE = 'Get Back on Track';

export const reactivationJob = () => {
  cron.schedule(
    '0 11 * * *',
    async () => {
      try {
        const now = dayjs();
        let noTxChallengeCount = 0;
        let noTxNotifCount = 0;
        let noOpenNotifCount = 0;

        // ── Check 1: No transaction in 14 days → challenge + notification ──
        const usersWithWallets = await prisma.users.findMany({
          select: {
            id: true,
            created_at: true,
            wallets: { select: { id: true, name: true } },
          },
        });

        const getBackOnTrackChallenge = await prisma.challenges.findFirst({
          where: { title: GET_BACK_ON_TRACK_TITLE, is_active: true },
        });

        for (const user of usersWithWallets) {
          if (user.wallets.length === 0) continue;

          const lastTx = await prisma.transactions.findFirst({
            where: { user_id: user.id },
            orderBy: { date: 'desc' },
            select: { date: true },
          });

          const baselineDate = lastTx?.date ?? user.created_at; // fallback if never transacted
          const daysSinceLastTx = now.diff(dayjs(baselineDate), 'day');
          if (daysSinceLastTx !== 14) continue;

          const [suggestedCount, activeCount] = await Promise.all([
            prisma.user_challenges.count({ where: { user_id: user.id, status: 'SUGGESTED' } }),
            prisma.user_challenges.count({ where: { user_id: user.id, status: 'ACTIVE' } }),
          ]);

          const primaryWallet = user.wallets[0];

          if (getBackOnTrackChallenge && suggestedCount + activeCount < 3 && suggestedCount < 2) {
            await userChallengesService.assignChallengeToUser(getBackOnTrackChallenge.id, primaryWallet.id);
            noTxChallengeCount++;
          }

          await sendPushNotification({
            userId: user.id,
            title: 'We miss your logs 📉',
            body: `You haven't logged a transaction in 2 weeks. Let's get back on track!`,
            type: 'CHALLENGE',
            invalidateKeys: ['user-challenges'],
            data: { screen: 'Challenges' },
          });
          noTxNotifCount++;
        }

        // ── Check 2: No app open in 14/21 days → notification only ──
        const inactiveUsers = await prisma.users.findMany({
          select: { id: true, last_active_at: true },
        });

        for (const user of inactiveUsers) {
          const daysSinceActive = now.diff(dayjs(user.last_active_at), 'day');

          if (daysSinceActive === 14) {
            await sendPushNotification({
              userId: user.id,
              title: 'Come back to Aivinn 👋',
              body: `It's been 2 weeks — your finances are waiting for you!`,
              type: 'SYSTEM',
              invalidateKeys: [],
              data: { screen: 'Home' },
            });
            noOpenNotifCount++;
          } else if (daysSinceActive === 21) {
            await sendPushNotification({
              userId: user.id,
              title: 'We still miss you 💙',
              body: `It's been 3 weeks since you last opened Aivinn. We're here whenever you're ready.`,
              type: 'SYSTEM',
              invalidateKeys: [],
              data: { screen: 'Home' },
            });
            noOpenNotifCount++;
          }
        }
